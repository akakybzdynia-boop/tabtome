# Политика подписи кода

Эта политика относится к Authenticode-подписям официальных Windows-релизов TabTome.

## Что разрешено подписывать

- `TabTomeHost.exe`;
- `TabTomeSettings.exe`;
- `TabTome-Setup-<версия>.exe`.

Тестовые сборки, архивы расширения и исходников, сторонние бинарные файлы и произвольные файлы подписывать сертификатом проекта нельзя. Подпись подтверждает издателя и целостность файла, но не заменяет проверку исходников, тесты и антивирусный контроль.

## Ответственные роли

- автор изменений и сопровождающий релизы: `@akakybzdynia-boop`;
- отправитель и подтверждающий запросы подписи: тот же сопровождающий, пока у проекта один разработчик;
- закрытым ключом и сертификатом управляет SignPath. Проект не получает и не хранит закрытый ключ.

Если у проекта появятся другие сопровождающие, подготовку релиза и подтверждение подписи следует разделить между разными людьми, если роли аккаунта SignPath это позволяют.

## Порядок выпуска

1. Исходный код релиза фиксируется в публичном GitHub-репозитории.
2. Обычный Windows CI собирает и проверяет код на GitHub-hosted Windows runner.
3. Создаётся тег `windows-v<версия приложения>`, например `windows-v0.11.1`.
4. Из этого тега вручную запускается workflow `Windows SignPath release candidate`.
5. Workflow выполняет чистую сборку, все тесты и подготавливает установщик закреплёнными версиями Node.js и Inno Setup.
6. SignPath подписывает приложение настроек и Native Messaging host.
7. Подписанные внутренние EXE помещаются в установщик; затем отдельно подписывается итоговый EXE установщика.
8. Workflow проверяет Authenticode и выполняет изолированный тест установки и удаления.
9. GitHub Release публикуется отдельно и только по осознанному решению. Workflow подписи ничего не публикует и не изменяет репозиторий.

Конфигурации допустимых артефактов хранятся в `.signpath/`. В секрете GitHub хранится только API-токен SignPath, а не сертификат или закрытый ключ.

## Контроль версии и метаданных

- версия приложения читается из `server/package.json`;
- тег обязан совпадать с `windows-v<версия приложения>`;
- SignPath проверяет ожидаемые пути, название продукта, компанию и версии файлов;
- SHA-256 вычисляется заново только после получения и проверки подписанного установщика.

## Компрометация и злоупотребление

При подозрении на взлом GitHub, SignPath или аккаунта сопровождающего подпись немедленно прекращается. Нужно отозвать токены и сессии, обратиться в SignPath для приостановки или отзыва сертификата, убрать недоверенные файлы из раздачи, сообщить затронутые версии и возобновить выпуск только после восстановления доверенной среды.

Нельзя обходить ошибку подписи и публиковать неподписанный файл под тем же именем официального релиза. Неподписанные тестовые сборки должны быть явно обозначены и не размещаться среди официальных загрузок.

## Проверка пользователем

```powershell
Get-AuthenticodeSignature .\TabTome-Setup-0.11.1.exe | Format-List Status,StatusMessage,SignerCertificate
Get-FileHash -Algorithm SHA256 .\TabTome-Setup-0.11.1.exe
```

У официального подписанного релиза статус должен быть `Valid`, а SHA-256 — совпадать с опубликованной контрольной суммой именно этого релиза.

## Конфиденциальность

При подписи в SignPath не отправляются страницы пользователя, SMTP-пароли, EPUB и настройки приложения. SignPath получает только сборочные файлы и метаданные сборки/репозитория, необходимые для проверки происхождения и подписи релиза. Политики конфиденциальности: [русская](landing/ru/privacy/index.html) и [английская](landing/en/privacy/index.html).

Бесплатная подпись кода предоставлена [SignPath.io](https://signpath.io/), сертификат — SignPath Foundation.

## Текущий статус

Интеграция и политика подготовлены, но нельзя называть файлы подписанными Authenticode до одобрения заявки SignPath и успешной проверки подписей в реальном workflow.
