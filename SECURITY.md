# Security model

TabTome 0.11.1 does not listen on a TCP port. Firefox starts the registered Native Messaging host and communicates over a private stdin/stdout channel. The native application manifest allows only extension ID `page-to-ereader-local@local`; ordinary web pages and unrelated extensions cannot ask Firefox to open this channel.

The generated Chrome package is not yet authorized by the Windows native-host installation. Chrome requires a separate manifest with an exact `chrome-extension://<ID>/` entry in `allowed_origins`; wildcards are forbidden. Until a stable Chrome ID is assigned and registered, the Chrome UI build cannot open the native channel. This deliberate incomplete state is not bypassed with a broad origin.

`allowed_extensions` is Firefox authorization, not authentication performed by the executable itself. Any process already running as the current Windows user can directly start `TabTomeHost.exe`, provide framed input over stdio, read local configuration and modify the project files. This is explicitly outside the threat model; Native Messaging prevents exposure to websites and unrelated Firefox extensions, not compromise of the Windows account.

The protocol accepts only `health`, `smtp-check`, `job-status`, `settings-get`, `settings-save` and `send` commands. Input is validated, inbound frames are limited to 32 MB, outbound frames to 1 MB, articles to 25, HTML to 5 MB per article, pasted text to 1,000,000 characters, images to known JPEG/PNG/GIF signatures, and generated EPUB files to 18 MB. Plain text is XML-escaped; rich HTML is allowlist-sanitized again by the native component, and image references are rewritten to verified EPUB resources. `settings-save` accepts a validated sender, up to two fixed destination profiles, a default destination, and allow-list acknowledgements. It cannot set or read an SMTP password.

Article bodies and images are held in memory while the background task and short-lived host are running. An unfinished pasted-text draft may be stored in Firefox `storage.session`, which is memory-only, limited by this project to 8 MB and cleared when Firefox exits; oversized drafts are retained without images. The draft is removed when a text send is accepted. It is never written to the project's disk history. The extension does not request `clipboardRead`: data enters the system only through a user-initiated paste or drop into the editor, or as the selected plain text supplied by a user-invoked Firefox context-menu event. A remote image URL in pasted HTML is retained only as inert metadata; the editor does not assign it to `src` and therefore does not fetch it on paste. An explicit send downloads such images without cookies or HTTP authentication, rejects redirects and literal loopback, private, link-local, reserved and `.local` hosts. If any pasted image cannot be accepted or prepared, the UI warns before submission or aborts the send with a visible count instead of silently producing an incomplete EPUB. The eight-day disk ledger stores only job identifiers, state transitions, per-tab status, compact results and short errors. A durable `sending` marker is written before SMTP; if this write fails, SMTP is not started. An abandoned `sending` marker becomes `interrupted`, never an automatic retry.

The installed version keeps `data\settings.json` under `%LOCALAPPDATA%\PageToEreaderLocal`; a source-tree installation keeps it under `server\data`. The file stores the sender address, configured Kindle/PocketBook recipients, the default recipient and allow-list acknowledgements as plain JSON readable by the current Windows account. It contains no SMTP password. Send commands contain only the fixed recipient identifier; the native host resolves the actual address locally. PocketBook addresses are restricted to `@pbsync.com`, and a durable job ID cannot be rebound to another recipient.

Protocol stdout contains only length-prefixed JSON frames. Logs are written to files, rotate at 5 MB and redact email addresses and 64-character token-shaped strings. Logs must not receive article HTML or passwords.

The installed version keeps `.smtp-pass` under `%LOCALAPPDATA%\PageToEreaderLocal`; a source-tree installation uses `server\.smtp-pass`. It uses Windows DPAPI and protects an offline copy from another Windows account, but the password must be decrypted into the host process memory during SMTP authentication. Decryption is lazy: `health` and `job-status` do not launch PowerShell or expose the password; `smtp-check` and `send` decrypt it into captured child-process output. DPAPI does not protect against malicious software already running as the same Windows user.

Version 0.11.1 does not accept `SMTP_PASS` from `.env` or the inherited process environment during normal operation. On Windows, a legacy assignment in `.env` is migrated before configuration is loaded: DPAPI encryption is created and round-trip checked first, then a same-directory temporary file atomically replaces `.env` without any `SMTP_PASS` assignment. If protection, verification or replacement fails, SMTP startup is blocked and the original plaintext file remains available for recovery. If an existing DPAPI password conflicts with `.env`, neither value is overwritten automatically.

The installer separates replaceable application files in `%LOCALAPPDATA%\Programs\TabTome` from mutable user data in `%LOCALAPPDATA%\PageToEreaderLocal`. Both remain writable by the current user, so this design covers hostile web pages, unrelated extensions, accidental network exposure and offline access from another account. It does not protect a compromised Windows session, a malicious extension with the same signed ID, or modified local application files.
